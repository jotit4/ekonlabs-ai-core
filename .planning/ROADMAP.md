# Roadmap — v1.2 Human-Feeling Agent

**Milestone:** v1.2 Human-Feeling Agent
**Goal:** Make the agent feel like a human receptionist — patient should not notice they are talking to a bot, either conversationally or in how effectively their problem gets resolved
**Timeline:** 1 week (5 working days, ~1 day per phase)
**Phases:** 5 (numbered 11–15, continuing from v1.1 which ended at Phase 10)
**Coverage:** 22/22 requirements mapped

## Phase Details

### Phase 11: System Prompt & Model
**Goal**: The LLM enters every conversation with a complete persona directive, clear protocol instructions, and the capability to call search_knowledge_tool, running on the correct model at the correct temperature
**Depends on**: Nothing (pure configuration, zero behavior risk, unblocks all other phases)
**Requirements**: PROMPT-01, PROMPT-02, PROMPT-03, PROMPT-04
**Success Criteria** (what must be TRUE):
  1. The DEFAULT_SYSTEM_PROMPT is at least 400 tokens and contains persona, voseo directives, booking protocol, identity rule, and at least 2 few-shot tone examples
  2. The system prompt contains an explicit instruction to call `search_knowledge_tool` for any clinic-specific information (prices, schedules, services, policies)
  3. The LLM model identifier in generation.py is `gpt-4.1-mini` (not `gpt-4o-mini`)
  4. The LLM temperature in generation.py is `0.5`
**Plans**: 11-01-PLAN.md

### Phase 12: State Schema Extension
**Goal**: ConversationState carries the three new fields required for multi-turn name collection without breaking any existing tests
**Depends on**: Phase 11 (clean codebase baseline before schema change)
**Requirements**: NAME-01
**Success Criteria** (what must be TRUE):
  1. `ConversationState` in state.py has `patient_name: NotRequired[str | None]`, `name_collection_active: NotRequired[bool]`, and `slot_presented_at: NotRequired[str | None]`
  2. All existing tests pass unchanged after the schema change (NotRequired fields are absent by default)
  3. A test that instantiates ConversationState without the new fields does not raise a KeyError or TypeError
**Plans**: 12-01-PLAN.md

### Phase 13: LLM-Generated Responses
**Goal**: The LLM writes every patient-facing response — slot presentations use natural prose, booking confirmations embed structured data verbatim, and the two deterministic bypasses (shadow mode, anti-diagnostic) remain hardcoded and unchanged
**Depends on**: Phase 12 (state schema must include new fields before generation_node is restructured)
**Requirements**: RESP-01, RESP-02, RESP-03, RESP-04, RESP-05, RESP-06, RESP-07
**Success Criteria** (what must be TRUE):
  1. A patient asking for available slots receives a response with no emoji-numbered lists; the exact slot display strings appear in the response; `_llm.invoke` is called (verified in tests)
  2. A booking confirmation response contains the exact `booked_slot["display"]` string character-for-character, wrapped in the LLM's natural Argentine Spanish prose
  3. A cancellation confirmation, a no-availability response, and an ambiguous-slot response are each generated by the LLM (not returned as Python f-string templates)
  4. Sending a medically diagnostic message still returns the hardcoded anti-diagnostic response without calling the LLM
  5. When shadow mode is active, the hardcoded redirect string is returned without calling the LLM
**Plans**: TBD

### Phase 14: LLM-Driven RAG via Tool Calling
**Goal**: The LLM retrieves clinic knowledge by calling search_knowledge_tool itself; the pre-fetch rag_retrieval_node becomes a no-op; tool call results appear as ToolMessages in conversation history
**Depends on**: Phase 13 (generation_node must be restructured before tool binding is added to its LLM path)
**Requirements**: RAG-01, RAG-02, RAG-03, RAG-04
**Success Criteria** (what must be TRUE):
  1. A patient asking a clinic-specific question (price, schedule, service) causes the LLM to call `search_knowledge_tool`; the tool result appears as a ToolMessage in `state["messages"]`
  2. `rag_retrieval_node` returns `{}` and does not populate `rag_context`; the graph edge from rag_retrieval to generation is preserved
  3. For non-booking, non-scheduling messages, `tool_choice` is forced (not `"auto"`); the LLM does not answer clinic-specific questions from training data
  4. If the tool returns an empty result, the LLM responds with "no tengo esa información" (or equivalent) — it does not hallucinate clinic data
**Plans**: TBD

### Phase 15: Patient Name Collection
**Goal**: The agent asks for the patient's full name before confirming any booking, collects it within 2 turns, creates the calendar event with the patient's name in the title, and hands off to human staff if the name is not provided after 2 attempts
**Depends on**: Phase 13, Phase 14 (generation_node must be in its final form; RAG path must be stable before adding name-capture gate)
**Requirements**: NAME-02, NAME-03, NAME-04, NAME-05, NAME-06, NAME-07
**Success Criteria** (what must be TRUE):
  1. When a patient selects a slot and no `patient_name` is in state, the agent asks for their full name before the calendar event is created — no event exists in Google Calendar until the name is captured
  2. When the patient replies with their name, the agent confirms the booking in that same turn and the Google Calendar event title is "Turno — [Full Name]"
  3. During name collection, sending a booking confirmation keyword (e.g. "listo", "dale") does not create a duplicate booking or bypass the name request
  4. If the patient does not provide a name after 2 prompts, `is_paused=True` is set and the conversation routes to human handoff
  5. The slot validity is re-checked against Google Calendar if more than 30 minutes have passed since `slot_presented_at`
